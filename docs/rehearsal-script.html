Rehearsal script

Walk the J1–J8 journeys and G1–G7 guarantees on the deployed build, using two real phones and approved inboxes. Record what happens; this checklist is not evidence that a run passed. Keep it current: a PR that adds or changes something a coach, family or operator can see adds its live check here in the same PR.

Before the run

Events are required and are being built slice by slice. TRAK-25 has nine acceptance checks and 18 implementation issues (TRAK-124–141); their status lives in Linear. The final rehearsal cannot pass until all nine checks below pass. Earlier journey passes do not waive the event gate.

  • Read MVP Requirements, the operational runbook and the release gate. Record commit, workflow, served build, backend target, operator and start time.
  • Use designated synthetic roles and an approved roster: two siblings and a child whose guardian withholds consent, plus a separate academy for isolation tests. Exercise both email activation and a child without email. Prepare a synthetic squad of at least 25 players for the size check.
  • Use approved Gmail and Microsoft/Outlook inboxes for real delivery checks. Prepare an iPhone, an Android phone with Google Calendar and an Outlook account; record device, browser and calendar-app versions. Do not use invented addresses at real mail providers.
  • For J8, enable events for the designated synthetic academy and leave the other off, using the implemented operator control once available. Record the switch state and test its off behavior; this script supplies no speculative SQL.
  • Time zones (TRAK-175, being built): “Dubai time” below means the academy’s own time zone. Rehearsal FC stays on Dubai (UTC+4 all year). Once TRAK-175 is live, repeat J8·1–3 and the reminder check for a synthetic academy on Europe/Athens, with one event before and one after the 25 Oct clock change (UTC+3, then UTC+2): a 17:00 event reads 17:00 in the app, the email, the reminder, the register and the calendar, on a phone set to any zone.
  • Two squads under one coach (TRAK-176, not built yet): one coach holds a U14 and a U16 squad. Until TRAK-176 is live, a coach’s event reaches every child on their roster, so a two-squad coach fails J8·2. Once it is live, prepare a synthetic coach with both squads and run the two-squad case below.
  • There is no staging environment. Coordinate writes and fixture cleanup on the shared backend. Existing seed data does not prove admission, consent, email delivery or calendar behavior.
  • Record pilot cohort/window and count_synthetic before changing them for a designated run; restore the agreed state afterwards. Real-pilot reports must exclude synthetic accounts.
  • The academy briefing is still pending. No staging, daily backups retained for seven days and no PITR remain disclosures to make before launch. The restore rehearsal on an isolated copy (TRAK-150) is part of these live tests; record its measured recovery time here.

Check boxes are working notes only. Put durable, redacted evidence on the assigned issue: commit · deployment · device · synthetic identity · date/time · expected/observed result. Do not include passwords, codes, tokens, full calendar links or family data.

Admission, consent and recovery

J1

Load the academy-supplied roster

Use the operator loader dry run, review it, then apply only the agreed synthetic rows. Verify the coach sees each child’s correct waiting/approved state. Repeat the load and check that it does not create duplicates.

Record: Exact roster IDs, expected membership, repeat result and any partial-load failure. A coach cannot add a child or link one by a TRK code. A row for a child younger than the academy's minimum age (13 for UAE academies) by date of birth is refused by the loader's dry run and by the database (TRAK-165); check one on the synthetic roster, and that an academy admin can't lower the minimum.

J2

Guardian invitation and consent

Send the approved guardian invitation through the roster flow to Gmail and Microsoft/Outlook inboxes. Check that it reaches the inbox, not spam, in under 60 seconds, with the correct child, academy, purpose and safe-sender/Trak branding. Open its code-entry page; verify that opening the page alone does not consume the code, then type the code. Confirm both siblings appear and grant each approval separately. Test the second-child email for an existing guardian as well as a new guardian. Keep the other family withheld.

Record: Send and inbox-receipt times for each provider, sender/branding, correct recipient and child, sibling list and distinct consent records. Each saved consent carries notice version 2026-10-09.1, with no separate “see their progress” choice (TRAK-145). An operator invite for a synthetic child whose guardians all have reserved test addresses (@rehearsal.trak.test) answers sent: 0 with unmailable_address for each, and leaves invited_at empty (TRAK-94). Do not mark mail sent as mail received.

J3

Activate email and username children

Before consent, verify activation/development access is refused. After consent, complete the email child’s invitation and verify the roster name. Cover new and existing accounts, expired and already-used codes, and resend: the old code must fail and the latest must work. Record an unavailable resend flow as open. For a child without email, have the guardian create a username/password through the consent flow, then sign in as that child.

Record: No child email sent before consent; expected outcomes for each account/code/resend case; the no-email child needs no mailbox. The child cannot choose a different identity, age or academy. With the guardian’s home open on another device, the “Waiting for … to sign up” card clears when they return to the tab, with no refresh (TRAK-121).

J3

Exercise password recovery

For an email account, use Forgot password, type the latest recovery code, and set a password. Reject a used or wrong code. For a username child, the guardian opens Profile → the child’s login card → Set a new password while the child’s other device remains open.

Record: Actual sign-out timing, weak-password feedback, and the partial-failure message if sessions cannot be ended. A copied access token may survive until expiry; UI sign-out alone does not prove token revocation.

G2/G5

Check wrong-account boundaries

Attempt the invitation/recovery flow with another account already signed in. Check sibling consent and child login details stay attached to the intended guardian and child.

Record: Expected refusals and controls showing the correct account can complete its own flow. Never substitute a real third-party inbox.

Coach records and family readback

J4

Log and edit sessions

As the assigned coach, log training with attendance and a match with distinct per-player minutes, goals and assists. Check saved values and edit a saved session. Run the agreed check on the synthetic squad of at least 25 players.

Record: No invented match defaults, duplicate writes or unexplained errors; attendance and edits persist. An impossible score (two scorers in a 1–0 win) is refused with a reason the coach can act on (TRAK-149, TRAK-151), and so are more assists than goals (two assists in a 1–0: "2 assists entered, but the team scored 1", TRAK-167). Saving a match again with another score, or adding a scorer whose goal would pass the saved score, saves nothing and says which: no second session or attendance appears in history (TRAK-153). The same opponent on another day saves as a new match. Use the routed session flow, not an old Quick Match Log component.

J5

Assess and publish

Assess a player for a completed session they attended. Change the six ratings and write a player message plus a distinct private note. Publish, then edit and save. Also try an unattended session. For a child awaiting consent, the coach may view the academy-supplied profile, but assessment creation must be blocked.

Record: Pre-consent profile visibility and blocked assessment creation separately; one assessment per player/session; only the intended coach can write; refused writes preserve an understandable outcome. Quick Assess is outside pilot scope.

J6

Read as each family member

As the player, open home and session history; confirm bands, bars and the published message. As guardian, inspect both assessed siblings, their history and alerts; switch child and return. Exercise a failed load and an empty history.

Record: The selected child’s records only. Neither child nor parent sees private notes; parents do not see the coach message. Failed loads show errors rather than a false empty state.

J7

Read the weekly measures

Have an authorized operator query pilot_j7_this_week using the runbook. Compare the counts with the actions just performed; repeat a view/save and check the distinct counting behavior.

Record: Assessments per coach, player opens and parent opens within one minute, including the cohort/window and synthetic setting. A player “open” means home displayed the message, not deliberate reading.

Withdrawal and isolation

G1/G6

Withdraw with sessions open

Keep a coach form, child app and a second guardian session open. Withdraw the last active approval for one child and retry the coach save. Check readback and return to the other open tabs. Separately withdraw approval before a child finishes setup.

Record: Server write refusal and withdrawn content behavior, including timing and offline limitations. With multiple guardians, distinguish one withdrawn approval from withdrawal of the last active approval. A guardian who deletes their account: the confirmation says it withdraws their approvals, and afterwards their child's approval reads as withdrawn, with the evidence row kept (TRAK-155).

G3–G7

Run negative checks under real roles

Use the deployed-backend checks for family/academy isolation, private notes, wrong-recipient protection and pilot-disabled AI/photos/sharing. Include positive controls showing the target data exists and is accessible to its correct owner.

Record: Test identity, expected denial, actual result and control result. Source inspection, service-role reads or an empty database cannot prove isolation.

J8 · TRAK-25 · required before real families receive events

Events and phone calendars

These are the nine acceptance outcomes in TRAK-25, as expanded on 8 October, and MVP Requirements. The numbers below identify acceptance checks, not the implementation issue numbers. Check each one as soon as its slices are live; then record all nine on the same deployed build with synthetic families and real phones.

J8 · 1

Weekly scheduling

Create eight weeks of weekly training. Repeat once from a phone set to another time zone (for example Athens or New York).

Record: Elapsed time is under two minutes. Every week lands at the Dubai time entered, whatever the phone’s time zone. A match cannot be saved as a series. The day and start time are picked on Arc’s date and time pickers; Save with no start time says “Pick a start time”, and no event of any kind saves without one (TRAK-157).

J8 · 2

Changes and cancellations reach families

Change and cancel events; check every affected player and guardian on next app load, including the selected child’s parent bell and the player’s event alert. Test changes for today and tomorrow in Dubai time, including venue and meet time. Cancel a published match five days out: it is emailed too, while moving it (not today or tomorrow) is not. Make three quick edits and check that only the final change is emailed. Cancel one with the coach’s phone put in airplane mode straight after Save: the email must still arrive, sent by the scheduler’s sweep rather than the app (TRAK-136). Open an event and save without changing anything. Save an event as a draft without publishing it.

Record: Correct, consented guardian recipients only; the email arrives in Gmail and in the Microsoft 365 inbox within 60 seconds, in the Inbox (not Junk, spam or Other), with SPF, DKIM and DMARC = pass in the headers. Microsoft's link scanner opening it changes nothing. Record send time and inbox receipt metadata. No child name in the subject, coach notes or state-changing link. Record failed-delivery visibility/retry. The edit-collapse window is 15 seconds (live run 11 Oct; accepted for the pilot, Imad 12 Oct): two saves more than 15 s apart send two emails, the second one correct. A move or a cancellation shows once in the parent bell, unread until marked read (one by one or Mark all read; closing the bell keeps the count; the Unread tab lists what's new; Dismiss removes one until the coach changes it again), and a row's Open event opens the event page; siblings are counted per child. A player's bell does the same for their squad (TRAK-163). An unchanged save shows no “Changed”, updates no calendar and sends no email (TRAK-152). A cancellation reason that names a squad child or holds a link shows nowhere a family looks: event page, parent bell, player bell, email, calendar or WhatsApp text (TRAK-164); the coach's own schedule still shows it. A draft reaches no one: app, bell, calendar, email or share text.

J8 · 3

Apple, Google and Outlook subscriptions

Subscribe with a personal link using Apple, Google and Outlook on the two real phones. Create, change and cancel events, then refresh each calendar.

Record: New, changed and cancelled events appear after refresh with no duplicates, stable occurrence IDs and correct Dubai times. On a phone set to another time zone, kickoff moves to the phone’s clock and the meet line reads “Meet 1 h 30 min before kick-off (12:30 Dubai time)”: relative to kickoff, with the clock time labelled (TRAK-169). Each person has their own link; it stops working on their next fetch after consent is withdrawn or the coach leaves (TRAK-132). Record the feed’s last-fetch time separately from the calendar’s displayed update and any cache delay.

J8 · 4

Withdrawal removes event access

Withdraw the child’s consent, then request the app’s events and the existing calendar link again.

Record: The child’s events are absent on the next request; an authorized sibling remains available. Record what a calendar app retains in its local cache separately. Replacing a link or removing access cannot erase an already downloaded copy.

J8 · 5

No cross-academy event visibility

Run real-role SQL access tests against populated events in two academies. Verify the disabled academy separately, including refused writes and missing/error configuration failing closed. Exercise authorized access while enabled so the switch cannot mask a missing isolation policy.

Record: All unauthorized reads are refused/empty; positive controls show the same rows to the correct academy.

J8 · 6

No child names in calendar entries

Inspect the actual subscription entries and displayed calendar content.

Record: No child name or coach note in an event title, description, location or other calendar entry field. Inspect content returned by the feed as well as what each calendar displays.

J8 · 7

Past event becomes an attended session

On a past event, Take register should prefill everyone present except reported absences. Correct the actual attendance, save to create/link a completed session in one step, then retry. A match should open the existing match log with its date and opponent.

Record: Correct attendance/session result and no duplicate on retry; a withdrawn child cannot be marked present. Assessment selection offers attended sessions, and J4/J5 remain green. Future events must not expose Take register. The register opens pre-filled as present; one tap marks a child absent, and saving makes it the completed session (TRAK-138). Pre-filled absences need the parent’s Can’t make it button (TRAK-137, not built yet).

J8 · 8

Complete the final two-phone run

Complete the production rehearsal with synthetic families, the iPhone, Android phone and all three calendar apps. After J8, rerun J1–J7 and G1–G7 on this same final build.

Record: One evidence record ties all nine checks to the build, devices, roles and UTC times before any real family receives events. Preserve database readback, Auth/function logs, inbox receipt times and calendar refresh results before cleanup. A workaround is not a pass.

J8 · 9

One-tap calendar setup

As parent and player, use the last signup step to add the personal calendar on iPhone, Android/Google and Outlook. The native choice appears first, with other calendars available. Also skip setup, finish signup and subscribe later from Settings → Calendar.

Record: The real device handoff and subscription result for each provider, including Android behavior. Settings → Calendar → Get a new link must make the old link unusable on its next fetch. Record the working resubscription procedure; do not treat an unproved fallback as one-tap success.

Exercise the specified operating cases as their slices are delivered

These support the nine checks; they do not create a tenth acceptance check or claim that a pending feature is available.

  • Change and cancellation emails (TRAK-135): the subject is generic (e.g. “Training cancelled: Wed 14 Oct”), not the coach’s event title; a cancel reason is shown only when it names no squad child and holds no link; a link in the venue reads “(link in the Trak app)”; the footer says who to ask, and there is no Reply-To.
  • Import parked (TRAK-162): no coach sees “Import fixtures” anywhere (Schedule, Home, menus) while the CSV import is parked. Skip the next line until it returns.
  • Import and kit (TRAK-129, parked): preview 12 CSV fixtures, correct a bad row, confirm 12 matches and re-import with zero duplicates. Verify date, kickoff, meet time, opponent, home/away, venue and kit. No writes occur before confirmation, and the “Added N” count equals the rows actually saved. CSV only (PDF reading is out for now); no AI parsing.
  • Family event lists (TRAK-130, TRAK-131): as the guardian of two children, open each child’s upcoming events and one event page; as the player, check the Home week strip and Sessions list; neither player nor parent Home repeats a Next up card (TRAK-171). A guardian whose child has no consent sees no events for that child.
  • No overlapping events (TRAK-158): publish a training that overlaps a published match the same day: it is refused, naming the match and its times. Moved to start as the match ends, it publishes; a draft may overlap, and a cancelled event never blocks.
  • Upcoming lists (TRAK-170): player Sessions and parent Matches show the next 3 events, then “See more (N)”, which lists the rest; matches and history follow straight after.
  • Child switch on a slow load (TRAK-173): as a parent of two on a throttled connection, switch child the moment Home appears: the chosen child sticks, and the bell and lists show that child, not the first one.
  • Absence (TRAK-137) — known open: only the database half is live (#260); the parent’s Can’t make it button on the event page isn’t built yet. When it ships: the linked guardian reports Can't make it for one child, optionally adds a reason, then undoes before start. The coach sees it after one reload; the sibling is unaffected. Guardians of another child, withdrawn consent and players cannot submit it; families cannot see others’ absences.
  • Reminders (TRAK-136): check a two-day-ahead reminder, one email per guardian/day across their children, Settings → Notifications opt-out, and safe rerun without duplicate mail. Omit cancelled events and withdrawn children; email contains no unsubscribe action link and no “Can’t make it” line until its screen ships. Before merge the operator has enabled pg_cron and pg_net and set the scheduler token; after merge cron.job lists the three jobs and a run shows succeeded. Still owed — the first real send: give a synthetic family with a real inbox a published event two days ahead; the email arrives between 09:00 and 20:00 academy time, one event_reminder_sends row reads sent, and turning reminders off in Settings stops the next one.
  • Manual WhatsApp share (TRAK-139): on iPhone and Android, inspect training, match and cancellation text, including kit where applicable. No child names or absence lists; a cancellation reason that names a child or holds a link is left out, as in the email. The coach must choose a destination and send; opening the share control must not send.
  • Home header (TRAK-163): on coach, player and parent Home, the calendar button (top left) opens Schedule for the coach, Sessions for the player, and Events for the parent (TRAK-171); on Events, switch siblings and open each child’s own event; the name is in the centre, and a parent with two children switches child from it; the bell (top right) is on parent and player Home. The coach's Home has no "Smart Calendar" button.
    • This week: the strip runs Monday to Sunday (M T W T F S S) with today selected; each event is a dot (training blue, match green, other orange, cancelled red; the same colours as the coach calendar and the family lists, TRAK-159). On a Wednesday, Monday's session is still listed under M. Tapping a day lists its events; each opens to venue with (Home)/(Away), meet time and kit, and Open goes to the event page. The coach also sees drafts, marked Draft, and their logged match/training sessions, marked Logged. Open a logged session to its saved record; an event converted into that session appears only once, without an invented start time (TRAK-171). Check those same logged sessions on Schedule too. Coach B (events switched off) sees no strip. In airplane mode, reloading Home shows an error with Retry, never "Nothing planned" for every day.
    • Bell (Arc notification center): a new, changed or cancelled event raises the count by one on the next load, for the parent and for the player. Closing the bell keeps the count; the Unread tab lists what's new; Mark read (one alert) or Mark all read clears it; a row opens to its details, and Open event goes to the event page. The player also gets "New coach assessment" when their current assessment has a published message, for a training as well as a match; Open assessment opens that saved message. No unpublished message or private note reaches the bell, and switching player accounts clears the previous player’s alert (TRAK-171). The alert's time reads "1h" or "Yesterday", never a second event date (TRAK-160).
    • Dismiss: a dismissed alert stays gone after a reload, and comes back as "Changed" when the coach edits that event.
    • Siblings: with both children on the same squad, Mark all read for one child leaves the same event unread for the other.
    • After the update: a parent's alerts already seen before this release stay read (no flood of "new"). A player's first visit counts their upcoming events as unread once; that's intended.
    Record: device, role, the count before and after each step, and a screenshot of the header and strip at phone width.
  • Parent assessment history (TRAK-172, TRAK-174; live once #296 and #297 merge): as the parent of two, swipe the selected child’s last five band cards one at a time, then All assessments, which pages beyond 20. A training row on Matches opens that training’s exact assessment; a match row opens that match’s assessment, with Match details under it. A match or training the coach hasn’t assessed yet says “… hasn’t been assessed for this match yet” (or “session”), not an error. Switch child on any of these pages: the sibling’s bands never show, and no page shows the coach’s message or a private note.
  • Two squads, one coach (TRAK-176, once built): a coach with a U14 and a U16 squad switches squad from the header, like a parent switches child; roster, schedule, Home strip, assess list and register follow the chosen squad. A published U14 event reaches U14 families in the app, bell, email, reminder and calendar, and no U16 family; its register lists U14 players only.
  • Additional links (TRAK-140): this lower-priority slice follows the core work. When delivered, verify named extra links, one/all-child and match/all-event choices, independent revocation and last-fetch data. Revoking an extra link must not break the guardian’s own link; withdrawal/departure removes the affected access.

Not built yet, so the final run can’t pass without them: the parent’s Can’t make it button (TRAK-137), per-academy time zones (TRAK-175) and two squads under one coach (TRAK-176). Still unresolved: proof of the Resend sender's region and delivery (TRAK-126), the feed endpoint, the Android handoff/fallback, whether switching events off hides existing events and feeds, and exact operator recovery controls. Decided: same-day change emails also go to players who have their own email, and only published events reach families. Use the implemented specification for commands and retry procedures. Kit and absence reporting are in J8; lineups and broader matchday planning remain parked.

Close the run

  • Record every failed or unrun check as open. A wrong recipient, consent bypass or cross-child read pauses the affected scope and new admissions; follow the runbook’s incident process.
  • Preserve evidence before coordinating cleanup. Do not run a blanket purge on shared rehearsal data. Verify the intended pilot configuration and synthetic-account exclusion afterwards.
  • Update the assigned issues and journey index with the executed result. A founder-majority launch decision also needs the nontechnical launch gates, including academy briefing and counsel; a successful rehearsal alone does not admit real children.
